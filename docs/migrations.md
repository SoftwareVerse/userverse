# Database migrations

Userverse uses Alembic and supports PostgreSQL and MySQL in production. SQLite migration behavior is tested only as a development convenience; every schema change must work on both production engines.

## Apply and inspect migrations

```bash
make config-check
make migrate
uv run alembic current
uv run alembic heads
uv run alembic history --verbose
```

`docker-entrypoint.sh` applies `alembic upgrade head` when `RUN_MIGRATIONS` is true. For a single local container this is convenient. For multiple production replicas, use one deliberate migration job and set `RUN_MIGRATIONS=false` on API replicas.

## Create a migration

1. Start the selected development database.
2. Apply the existing migration head.
3. Change SQLAlchemy table models.
4. Generate a revision.
5. Review every autogenerated operation and its downgrade.
6. Test a clean upgrade against PostgreSQL and MySQL.

```bash
make db-up DB=postgres
make migrate
make migration MIGRATION="add account status"
uv run alembic upgrade head
make docker-test
```

Never accept autogenerated migrations without review. Pay special attention to UUID types, JSON defaults, booleans, indexes, foreign-key actions, check constraints, auto-increment behavior, and table alterations because dialect behavior differs.

## Production deployment

1. Back up the database using the provider's supported process.
2. Deploy the same immutable image to the migration job and API.
3. Run one migration container:

```bash
docker run --rm --env-file .env.production IMAGE_TAG true
```

4. Confirm `alembic current` reports the image's head.
5. Start API replicas with `RUN_MIGRATIONS=false`.
6. Verify `/`, Docker health, logs, and critical application flows.

## Rollback policy

Rolling back an image does not roll back its database. Do not run `alembic downgrade` automatically in deployment pipelines. Treat downgrade as a reviewed data operation, test it against a restored backup, and prefer backward-compatible expand-and-contract migrations for zero-downtime releases.
